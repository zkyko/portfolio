Silent failures: the bugs my own automation hid from me

The bugs I'm most afraid of aren't the ones that throw errors. A red build is loud — someone notices, someone fixes it. A green build that's lying is quiet, and it can ship wrong behavior for weeks.

Last year I built and ran three AI systems in production at Four Hands — a test-generation pipeline, an automated PR reviewer, and a request-to-PR workflow. Most of the hard work wasn't the "AI" part. It was finding and killing the silent failures. Here are three of them, and what they taught me.

1. The deploys that didn't deploy

My ticket-ingestion Logic App kept running the old model-based categorization logic — even though I'd replaced it with a deterministic tag check, redeployed, restarted the app service, and done a full stop/start cycle. The deployed file on disk was verified correct via a direct read, so the old code path should have been gone. To prove it was still running, I pulled the actual stored output for a ticket:

"Reasoning": "Ticket explicitly tests a non-Salesforce website with no
Salesforce login or functionality involved."
"IsSalesforce": "False"

That's genuine LLM-written reasoning — and factually wrong under the deterministic logic, which would have marked it True instantly from the [salesforce-qa] tag in the summary. The old model-based path was definitively still executing in production.

Root cause: build_workflow.py had a stray backslash in the $schema key — "\$schema" instead of "$schema" — probably there since the first version of the script. It's still syntactically valid JSON, and json.tool was the only check I'd ever run against the file. So every "VALID_JSON" confirmation passed while the platform silently refused to reload the running definition. Dozens of "successful" redeploys had changed nothing at runtime.

Fix: corrected the key, deleted the old workflow entirely, redeployed fresh. The lesson stuck: syntactic validity says nothing about semantic correctness. A JSON validator will happily bless a malformed $schema value.

2. The fallback that lied

I added a "content-sufficiency" gate — before generating a test, check that the ticket actually contains enough to test. The first real pipeline run silently fell back to sufficient: true on every ticket.

The bug: AOAI_ENDPOINT as a pipeline variable had no trailing slash (unlike the raw value az cognitiveservices account show returns), so string concatenation produced ...azure.comopenai/.... Not a local-test problem — I only caught it because the real task log showed:

getaddrinfo ENOTFOUND salesforceqa-ai.services.ai.azure.comopenai

I'd assumed from a local test that happened to use the slash-terminated form. The real environment didn't, and instead of failing loudly, the gate just silently said "yes, sufficient" to everything. The fallback was masking the outage.

3. The error report that reported nothing

When a generated test failed, the "Last error" in the Jira comment was lastError.slice(0, 500) — the first 500 characters of captured stdout. In practice, that entire range is BrowserStack SDK startup boilerplate ("Reading configs...", "SDK run started with id: ..."). The actual Playwright failure reason came after that, and never made it into the report at all. A user pasted in a real example: the whole "Last error" was startup logging, cut off mid-string. The thing we'd built to tell us why tests failed was, itself, silently broken.

What I built because of this: real failure diagnosis

These three failures shared a root theme — when something goes wrong, the system's first instinct is to hide it. So I rebuilt the failure path around one question: is this a bug in the test, or a bug in the app?

On final failure, instead of dumping a truncated slice, the pipeline now:

  1. Fetches the actual text of BrowserStack's console and Playwright logs for the failing session (not just the links).
  2. Sends the generated test code, the full raw error, and those logs to a model with an explicit instruction: is this a real app problem, or a test-script problem (bad selector, timing, strict-mode violation, wrong assumption)?
  3. Makes that diagnosis the Jira comment and the PR description.

And it works. Re-running a known-failing ticket, the diagnosis came back:

This is a test-script problem — specifically a wrong assumption about the page flow, not a real app outage. The username field passed, but the password locator timed out... Salesforce's stage login shows only the username field first; the password field only appears after the user submits the username.

The page had loaded fine the whole time — confirmed by watching the recording. The test's assumption about the login flow was wrong. That's exactly the kind of thing a video alone doesn't surface, and exactly the kind of thing that separates "the test is broken" from "the product is broken."

What I take into every system now

  1. Deterministic gates before anything expensive. Tag checks and content checks are free and don't call a model. Every ticket passes them before a single token is spent.
  2. Never trust a fallback to be honest. If a step can silently degrade to a default, instrument it so the default is visible.
  3. Validate against the real log, not the local test. getaddrinfo ENOTFOUND was in the production log, not my dev box.
  4. "Valid JSON" ≠ "correct JSON." A validator checks syntax, not intent.
  5. A failed run should still produce an artifact. The pipeline now always opens a PR — a failing run gets [NEEDS REVIEW — TEST FAILING] with the real diagnosis, instead of vanishing into a single Jira comment and losing 90%-right generated code.

None of this is glamorous. But this is what "shipping AI systems in production" actually means: 20% model calls and 80% making sure the thing doesn't silently lie to you.
